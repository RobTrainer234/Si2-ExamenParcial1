# CU-26 Returns, Restocking, and Credit Notes

Authority: `docs/casos-de-uso-oficiales-parcial-2.md`: “Gestionar Devolución y Reposición de Prendas”; Cajero/Vendedor and Admin Sucursal; Web and Flutter; in-store return; Kardex `RETURN`/`RESTOCK`; credit note. Keep this flow separate from CU-13 garment exchange.

## Confirmed policy decisions
- Support both partial and full returns by sale line and quantity; prevent returning more than purchased/already returned quantity.
- Settlement is a reusable, partial-balance credit note, tenant-bound, non-transferable, and non-expiring until a future policy is specified. Bind it to an existing customer. For an original sale with no `customer_id`, require the cashier to identify/select an existing customer during return before issuing the note.
- Log `RETURN` when goods are received. Increase sellable stock only via `RESTOCK` after condition inspection; record non-sellable returns without increasing available inventory.
- Either Cashier/Seller or Admin Sucursal with access to the original sale branch can complete the return; no dual approval. Return and note settlement are online/server-authoritative.
- Credit notes are redeemable partially on future in-store POS sales from Web and Flutter at any branch in the same tenant where the cashier has access. Preserve unused balance; apply existing in-store tender to any remaining amount. No live Stripe/QR refund integration.
- Flutter currently has no physical cashier POS; user explicitly approved a new staff-only Flutter POS flow for CU-26 returns and note redemption.
- User explicitly authorized adding tenant-scoped idempotency to `POST /sales/physical` because that endpoint currently cannot safely retry an ambiguous create. Create a migration artifact and tests; do not apply the migration.
