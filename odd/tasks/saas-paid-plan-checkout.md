# ODD Task Plan — SaaS Paid Plan Checkout

## Objective
Enable a prospective company to select a monthly or annual paid SaaS plan from the landing page, register its tenant administrator, complete Stripe recurring Checkout, and gain application access only after Stripe confirms successful payment. Preserve the separate no-payment 14-day free-trial flow.

## Problem and rationale
Paid plan links currently preserve `plan` and `billing` in the URL, but company registration always calls the BASIC trial endpoint, which grants access immediately. Stripe currently handles commerce PaymentIntents, not SaaS subscriptions. The accepted product decision is to keep trial signup separate and require confirmed payment before granting access for paid registrations.

## Scope
- Implement recurring Stripe Checkout for active BASIC/PROFESSIONAL plans with monthly/annual billing, deriving amount and currency from server-side plan data.
- Persist pending paid registrations and Stripe correlation identifiers; do not create an accessible tenant or issue auth tokens before payment confirmation.
- Activate tenant, ADMIN user, and subscription only after verified Stripe webhook confirmation; process repeated events idempotently and maintain access state for recurring subscription updates/cancellation/payment failure.
- Connect paid plan registration UI and Stripe hosted Checkout success/cancel return UX; keep `plan=TRIAL` on the existing free-trial path.
- Add backend/web tests and brief user-facing setup/testing documentation.

## Out of scope
- Changing the official partial CU numbering or CU-01 actor.
- Removing the free trial.
- Reusing commerce sale/PaymentIntent records or granting access from a browser redirect alone.
- Live-mode payment, real card charges, publishing, or committing.

## Constraints and evidence
- Landing links already carry `plan` and `billing`; `CompanyRegisterComponent` currently reads but does not submit them.
- `trial_signup` always assigns BASIC for 14 days and immediately issues JWT tokens.
- Existing Stripe code is commerce-specific; SaaS Checkout/webhook activation is absent.

## Acceptance criteria
1. Selecting a paid plan and interval creates a pending checkout using the server's exact nonzero price/currency and Stripe recurring interval.
2. Before verified payment, the prospective tenant cannot log in or use protected application functions, and no active subscription is provisioned.
3. A verified successful Checkout event creates/activates exactly one tenant, administrator, and subscription and stores provider identifiers.
4. Replaying a webhook cannot duplicate tenants, admins, subscriptions, or activation side effects.
5. Cancelled, expired, unpaid, invalid-signature, or failed-payment paths never grant paid access; recurring failure/cancellation updates access according to the documented mapping.
6. Existing explicit 14-day trial signup still grants the intended trial access without requiring payment.
7. Landing-selected plan and billing interval survive registration and are not client-authoritative for price.
8. Repeated/concurrent signup submissions and Stripe transport retries cannot produce multiple active checkout sessions for one registration; Stripe requests use an idempotency key.
9. Alembic-created schema accepts the initial pending row before its Stripe idempotency/session values are assigned.
10. Focused backend and web tests pass; exact command outcomes are recorded. Stripe test-mode flow is exercised if the configured Stripe account/CLI permits it; otherwise the external blocker is recorded.
11. Paid Checkout cannot be created until the registrant completes six-digit email verification; codes and checkout capabilities are hashed at rest, single-use, expiring, and rate-limited.
12. The Brevo verification message is never sent through the live Stripe redirect or webhook path; real email delivery uses explicitly configured sender identity and secrets, while tests mock Brevo.
13. A successful Stripe webhook atomically activates tenant/admin/subscription and enqueues exactly one payment-confirmation email; delivery retries cannot change payment activation.
14. The paid success page presents confirmed, pending, expired, and error states with a clear login handoff; the free-trial path remains unchanged and SPC-6 does not add the first-login wizard.
